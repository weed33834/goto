## 1. 目标

让桌面端用户能够：
1. 在设置页开启/关闭同步、配置自托管中继地址。
2. 查看已配对设备列表，移除设备。
3. 作为旧设备生成 8 位配对码（或二维码），供新设备加入。
4. 作为新设备输入配对码，完成与旧设备的 ECDH 握手并安全接收 SMK。

Phase 4a 不实现后台自动同步调度器（Phase 4b），也不实现安全硬化（Phase 4c）。

## 2. 范围

### 包含
- 桌面端主进程配对服务（`pairingService.ts`）
- 中继 HTTP 客户端封装（`relayClient.ts`）
- IPC 通道：`syncChannels.ts` / preload / renderer API
- 渲染层状态：`syncStore.ts`
- 设置页同步模块：`SyncSettingsPanel.tsx`、`PairingDialog.tsx`、`DeviceList.tsx`
- 单元测试与集成测试

### 不包含
- 后台同步调度、LAN/Relay 自动选择（Phase 4b）
- 传输层重放保护、握手超时、设备吊销贯通（Phase 4c）
- 移动端同步
- 官方托管中继

## 4. 关键组件

### 4.1 relayClient.ts
封装对 relay 的 HTTP 调用：
- `registerDevice(identity)` → `{ token, wsUrl }`
- `createPairingCode(token, identity)` → `{ code, expiresAt }`
- `claimPairingCode(code, identity)` → `{ token, wsUrl }`
- `refreshToken(token)` → `{ token }`

所有请求携带 Ed25519 签名，与 relay `routes.ts` 的校验对齐。

### 4.2 pairingService.ts
负责完整配对流程：
- **旧设备侧**：
  1. 注册到 relay（若未注册）。
  2. 调用 `/pairing-codes` 生成 8 位数字码。
  3. 启动一个 responder `RelayTransport` 等待新设备连接。
  4. 握手成功后，通过新增 `SMK_TRANSFER` 消息将 SMK 加密发送给新设备。
  5. 将新设备公钥写入 `sync_devices`。
- **新设备侧**：
  1. 输入配对码。
  2. 调用 `/claim-pairing-code` 获得 token。
  3. 通过 `RelayTransport` 连接旧设备（initiator）。
  4. 完成 `SyncSession` 握手。
  5. 接收 `SMK_TRANSFER`，保存 SMK 到 `safeStorage`。
  6. 将旧设备公钥写入 `sync_devices`。

### 4.3 syncChannels.ts
暴露给渲染层的 IPC：
- `sync:getState` → 返回 `{ enabled, relayUrl, devices, lastSyncAt }`
- `sync:setEnabled(enabled)`
- `sync:setRelayUrl(url)`
- `sync:generatePairingCode` → 返回 `{ code, expiresAt }`
- `sync:claimPairingCode(code)` → 返回 `{ success, deviceId? }`
- `sync:removeDevice(deviceId)`
- `sync:onStateChanged` (push)

### 4.4 syncStore.ts
Zustand store 管理：
- `enabled`、`relayUrl`
- `devices` 列表（设备 ID、名称、上次在线时间）
- `pairingCode` / `pairingExpiry`
- `loading` / `error`

### 4.5 UI 组件
- `SyncSettingsPanel`：开关同步、中继地址输入、设备列表容器。
- `RelayUrlInput`：验证 URL 格式，支持 `ws://` / `wss://`。
- `DeviceList`：展示已配对设备、移除按钮、上次同步时间。
- `PairingDialog`：旧设备展示配对码与二维码；新设备输入配对码。

## 5. 数据流

### 旧设备生成配对码
```
用户点击「添加设备」
  └─► pairingService.registerAndCreatePairingCode()
      ├─► relayClient.registerDevice(identity)
      ├─► 保存 token 到本地安全存储
      ├─► relayClient.createPairingCode(token, identity)
      └─► 返回 code → 渲染层展示
```

### 新设备输入配对码
```
用户输入配对码
  └─► pairingService.claimPairingCodeAndPair(code)
      ├─► relayClient.claimPairingCode(code, identity)
      ├─► 保存 token
      ├─► 创建 RelayTransport 连接旧设备
      ├─► SyncSession 握手
      ├─► 接收 SMK_TRANSFER 并保存 SMK
      └─► 注册旧设备到 sync_devices
```

## 6. 安全与隐私

- **配对码**：8 位数字，5 分钟 TTL，一次性，最多 5 次尝试，每设备 10 秒速率限制（由 relay 强制执行）。
- **SMK 传输**：仅通过已验证的 `SyncSession` 发送，使用临时会话密钥加密；relay 不持有 SMK。
- **Token 存储**：relay auth token 使用 `safeStorage` 加密保存。
- **设备移除**：Phase 4a 中仅删除本地 `sync_devices` 记录与 token；即时吊销会话留到 Phase 4c。
- **URL 验证**：中继地址必须显式指定协议，禁止明文提示用户。

### 偏差 4：早期重放保护（early replay protection）

**设计文档原始描述**

第 2 节"范围 / 不包含"明确将重放保护排除在 Phase 4a 之外：

> - 传输层重放保护、握手超时、设备吊销贯通（Phase 4c）

**实现的实际做法**

`SyncSession` 已实现基于 8 字节序列号 + 滑动窗口的重放检测，未等到 Phase 4c：

- `src/shared/sync/syncSession.ts:91` `DEFAULT_REPLAY_WINDOW = 64`
- `src/shared/sync/syncSession.ts:93` `SEQUENCE_BYTES = 8`，每条加密消息前缀 8 字节 BE uint64 序列号
- `src/shared/sync/syncSession.ts:109-112` 持有 `replayWindow`、`sendSequence`、`maxReceivedSeq`、`receivedSeqs` 状态
- `src/shared/sync/syncSession.ts:202-209` `send()` 自增 `sendSequence` 并把序列号前缀拼入明文，随 GCM authTag 一并完整性保护
- `src/shared/sync/syncSession.ts:258-279` `acceptSequence` 滑动窗口判定：新最大值清理被推出窗口的旧序号；窗口外的旧帧或重复帧静默丢弃
- `src/shared/sync/syncSession.ts:505-522` `handleEncryptedFrame` 解密后取序列号，`acceptSequence` 返回 false 时静默丢弃，不触发 `onMessage`
- `src/shared/sync/syncSession.ts:75-76` `replayWindow` 可注入，0 关闭（仅测试）

**偏差理由**

重放保护与传输加密耦合紧密：序列号必须随密文一起被 GCM authTag 完整性保护才能防止篡改，若延后到 Phase 4c 再加，事后补丁需要改动 `send` / `handleEncryptedFrame` 的线格式，破坏已固化的协议字节。在 syncSession 内一并实现，让序列号直接复用现有加密通道的完整性保护，零额外开销。重放帧静默丢弃（而非抛错）是为了应对 relay store-and-forward 合法补发重复帧的场景，避免触发上层 terminate + 重连造成抖动。握手超时、设备吊销等其他 Phase 4c 项目仍按原计划延后。

### 偏差 6：SMK 一致性检查

**设计文档原始描述**

第 4.2 节 `pairingService.ts` 新设备侧流程第 5 步：

> 5. 接收 `SMK_TRANSFER`，保存 SMK 到 `safeStorage`。

第 5 节"新设备输入配对码"数据流：

> ├─► 接收 SMK_TRANSFER 并保存 SMK

均描述直接保存，未提及与本地已有 SMK 的一致性校验。

**实现的实际做法**

initiator 解密 SMK_TRANSFER 后，若本机已存在 SMK，先用恒定时间比较验证两者一致，不一致拒绝配对并抛错；仅在本地无 SMK 时才落盘：

- `src/shared/sync/pairingService.ts:481-488` `receiveSmkAndFinalize` 中：
  ```
  const existing = await loadSyncMasterKey();
  if (existing && !bytesEqual(existing, smk)) {
    throw new Error('local SMK already exists and does not match the received SMK; refusing to overwrite');
  }
  if (!existing) {
    await saveSyncMasterKey(smk);
  }
  ```
- `src/shared/sync/pairingService.ts:519-523` `bytesEqual` 恒定时间比较，避免时序侧信道泄露前缀匹配长度
- `src/shared/store/slices/syncSlice.ts:532-537` `removePairedDevice` 在删除最后一个配对设备时同步删除 SMK，与此检查形成闭环：只有"还有配对设备"时才保留 SMK，避免孤儿 SMK 阻断新群组配对

**偏差理由**

多设备配对场景下，已持有 SMK 的设备若误连到另一个群组的配对码，直接覆盖本地 SMK 会导致该设备后续无法与原群组同步，且历史加密记录无法解密。一致性检查把"已配对设备"与"群组"强绑定：同群组二次配对（existing == received）幂等通过；跨群组误配（existing != received）显式失败，由用户决策。恒定时间比较防止通过耗时差异探测 SMK 前缀。`removePairedDevice` 在清空配对列表时删除 SMK，与此检查闭环：仅当仍存在配对设备时才保留 SMK。
