# TaskFlow 2.0 端到端加密同步架构设计

> 状态：设计完成，待实现 MVP
> 关联文档：[生物识别解锁设计](2026-06-21-biometric-unlock-design.md)

## 1. 目标

- 在多台设备之间安全同步 TaskFlow 数据（任务、保险库、分类）。
- 同步服务器/中继**无法读取**用户数据，实现端到端加密（E2EE）。
- 支持离线操作，联网后自动同步。
- 新设备加入需经现有设备授权，防止未授权访问。

## 2. 同步拓扑

采用**混合模式**：

1. **局域网直连（首选）**：设备在同一 LAN 下通过 mDNS 发现，直接建立 TCP/WebSocket 连接交换同步数据。
2. **自托管中继（fallback）**：无法直连时，通过可选的 Node.js 中继服务器交换加密同步包。
3. **离线优先**：所有写操作先落地本地 SQLite，同步线程在后台择机推送/拉取。

```
设备 A  ◄────LAN 直连────►  设备 B
  │
  └──── 加密同步包 ────►  自托管中继 Server  ◄──── 加密同步包 ────  设备 C
```

## 3. 密钥体系

### 3.1 同步主密钥（Sync Master Key, SMK）

- 256-bit 随机密钥，与登录主密码解耦。
- 用于加密所有同步记录（AES-256-GCM）。
- 每台设备使用 Electron `safeStorage` 保存 SMK。

### 3.2 设备身份密钥

- 每台设备生成 Ed25519 密钥对作为设备身份。
- 公钥在首次配对时通过加密通道广播给其他设备。
- 私钥保存在 `safeStorage` 中。

### 3.3 会话密钥

- 两台设备通信时，使用 ECDH (X25519) 临时密钥对协商会话密钥。
- 会话密钥用于加密传输层数据，生命周期限定在一次同步会话内。

### 3.4 新设备加入流程

1. 新设备生成临时 ECDH 密钥对。
2. 现有设备展示**配对码**（8 位数字 / Base32）或**二维码**。
3. 新设备输入配对码，双方通过中继或 LAN 完成 ECDH 握手。
4. 握手成功后，现有设备将 SMK 加密发送给新设备。
5. 新设备保存 SMK，后续同步使用该密钥。

## 4. 数据模型

### 4.1 同步记录（sync_records）

```sql
CREATE TABLE IF NOT EXISTS sync_records (
  id TEXT PRIMARY KEY,              -- table_name:record_id:v:version
  table_name TEXT NOT NULL,         -- tasks / vault_items / categories
  record_id TEXT NOT NULL,          -- 原始记录 ID
  version INTEGER NOT NULL,         -- 乐观锁版本
  encrypted_payload BLOB NOT NULL,  -- AES-256-GCM 加密后的 JSON
  updated_at INTEGER NOT NULL,      -- 毫秒时间戳
  deleted INTEGER DEFAULT 0         -- 软删除标记
);
```

### 4.2 同步状态（sync_state）

```sql
CREATE TABLE IF NOT EXISTS sync_state (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  local_clock INTEGER NOT NULL DEFAULT 0,   -- 本地逻辑时钟
  last_sync_at INTEGER                        -- 上次成功同步时间
);
```

### 4.3 设备注册表（sync_devices）

```sql
CREATE TABLE IF NOT EXISTS sync_devices (
  device_id TEXT PRIMARY KEY,       -- 设备公钥指纹
  public_key TEXT NOT NULL,         -- Base64 Ed25519 公钥
  name TEXT,                        -- 设备别名
  paired_at INTEGER NOT NULL,
  last_seen_at INTEGER
);
```

## 5. 加密细节

### 5.1 记录加密

```
encryptRecord(plaintextJSON, smk):
  iv     = randomBytes(12)
  cipher = AES-256-GCM(smk, iv)
  ciphertext = iv || authTag || encrypted
```

- SMK 不直接用于传输层，仅用于加密持久化同步记录。
- 同一记录的多个版本使用同一 SMK，不同 IV。

### 5.2 传输加密

- ECDH 握手后得到共享密钥 `sharedSecret`。
- 使用 `sharedSecret` 派生会话密钥：`HKDF-SHA256(sharedSecret, salt, 'taskflow-sync-v1')`。
- 会话消息使用 AES-256-GCM 加密。

## 6. 同步协议

### 6.1 消息类型

```typescript
type SyncMessage =
  | { type: 'HELLO'; deviceId: string; publicKey: string; nonce: string }
  | { type: 'OFFER'; encryptedPayload: string }        // ECDH 公钥 + 签名
  | { type: 'ANSWER'; encryptedPayload: string }
  | { type: 'MANIFEST'; records: { id: string; updatedAt: number; hash: string }[] }
  | { type: 'REQUEST'; recordIds: string[] }
  | { type: 'BATCH'; records: SyncRecord[] }
  | { type: 'ACK'; receivedIds: string[] }
  | { type: 'ERROR'; code: string; message: string };
```

### 6.2 同步流程

1. **发现**：LAN 中通过 mDNS 发现同账号设备；或连接配置的中继服务器。
2. **握手**：ECDH + Ed25519 签名验证，确认双方身份。
3. **交换清单**：双方发送各自拥有的记录摘要（id + updatedAt + hash）。
4. **请求缺失**：向对端请求本地缺失或较旧的记录。
5. **批量同步**：对端发送 `BATCH` 消息，本地解密并写入。
6. **确认**：发送 `ACK`，更新 `last_sync_at`。

### 6.3 冲突解决（MVP）

- 采用 **last-write-wins**：比较 `updated_at`，保留时间戳更大的版本。
- 版本字段 `version` 用于检测并发写入；如双方版本同时增加，后续可升级为 CRDT 或手动合并。

## 7. 中继服务器

### 7.1 职责

- 为无法直连的设备转发加密消息。
- 临时存储加密同步包（TTL 7 天）。
- 不保存也不具备解密 SMK 的能力。

### 7.2 接口（WebSocket）

```
POST /register-device
POST /claim-pairing-code
WS /sync?deviceId=...
```

### 7.3 部署

- 默认不启用；用户在设置中填入中继地址后开启。
- 提供 Docker 镜像：`taskflow/sync-relay:latest`。

## 11. 安全与隐私

- 中继服务器仅存储加密 blob，数据库索引按 `device_id` + `message_id` 分片。
- 配对码限时有效（5 分钟），过期自动失效。
- 设备可随时在设置中「移除设备」，移除后该设备无法再参与同步。
- 所有传输层消息包含 Ed25519 签名，防止中间人篡改。

> 回写日期：2026-07-04

### 偏差 1：SMK_TRANSFER 消息类型新增

**设计文档原始描述**

第 6.1 节定义的 `SyncMessage` union 共 8 种类型，未包含主密钥分发相关消息：

```typescript
type SyncMessage =
  | { type: 'HELLO'; deviceId: string; publicKey: string; nonce: string }
  | { type: 'OFFER'; encryptedPayload: string }        // ECDH 公钥 + 签名
  | { type: 'ANSWER'; encryptedPayload: string }
  | { type: 'MANIFEST'; records: { id: string; updatedAt: number; hash: string }[] }
  | { type: 'REQUEST'; recordIds: string[] }
  | { type: 'BATCH'; records: SyncRecord[] }
  | { type: 'ACK'; receivedIds: string[] }
  | { type: 'ERROR'; code: string; message: string };
```

第 3.4 节"新设备加入流程"第 4 步仅描述"现有设备将 SMK 加密发送给新设备"，未规定承载该动作的消息类型。

**实现的实际做法**

`SyncMessage` union 新增第 9 种类型 `SMK_TRANSFER`，由 responder 在握手 ready 后用会话 sendKey 加密本机 SMK 发送给 initiator：

- `src/shared/sync/syncMessages.ts:81-84` 定义 `SmkTransferMessage { type: 'SMK_TRANSFER'; encryptedSmk: string }`
- `src/shared/sync/syncMessages.ts:95` 将 `SmkTransferMessage` 纳入 `SyncMessage` union
- `src/shared/sync/syncMessages.ts:106` 将 `'SMK_TRANSFER'` 加入 `MESSAGE_TYPES` 常量
- `src/shared/sync/syncMessages.ts:235-237` 实现 `isSmkTransferMessage` 类型守卫
- `src/shared/sync/pairingService.ts:334-335` responder 调 `session.send({ type: 'SMK_TRANSFER', encryptedSmk })` 发送
- `src/shared/sync/pairingService.ts:451-453` initiator 在 `onMessage` 中按 `msg.type === 'SMK_TRANSFER'` 分支接收

**偏差理由**

原设计未规定 SMK 分发的承载消息，仅描述"加密发送"。实现需要一个独立的消息类型来区分 SMK 分发与普通数据同步消息（BATCH/MANIFEST 等），避免在数据通道里夹带密钥分发语义；同时让 initiator 能在 `onMessage` 中按类型显式分派到 SMK 落盘流程，与数据同步路径解耦。

### 偏差 2：方向性会话密钥（directional session keys）

**设计文档原始描述**

第 3.3 节"会话密钥"描述：

> 两台设备通信时，使用 ECDH (X25519) 临时密钥对协商会话密钥。
> 会话密钥用于加密传输层数据，生命周期限定在一次同步会话内。

第 5.2 节"传输加密"描述：

> 使用 `sharedSecret` 派生会话密钥：`HKDF-SHA256(sharedSecret, salt, 'taskflow-sync-v1')`。
> 会话消息使用 AES-256-GCM 加密。

两处均描述单一会话密钥。

**实现的实际做法**

实现用 HKDF 派生两个方向密钥：sendKey 用于本机发出的消息，receiveKey 用于解密对端发来的消息。双方共享同一 ECDH 共享密钥与 salt，但因角色（initiator/responder）相反，各自的 sendKey 对应对方的 receiveKey：

- `src/shared/sync/syncCrypto.ts:217-220` 定义 `SessionKeys { sendKey: Bytes; receiveKey: Bytes }`
- `src/shared/sync/syncCrypto.ts:232-242` `deriveSessionKeys(sharedSecret, salt, role, info)` 按角色派生：
  - `sendKey    = HKDF(ss, salt, '${info}|${role}->${peerRole}')`
  - `receiveKey = HKDF(ss, salt, '${info}|${peerRole}->${role}')`
- `src/shared/sync/syncSession.ts:107-108` SyncSession 持有 `sendKey` / `receiveKey` 两个字段
- `src/shared/sync/syncSession.ts:208` `send()` 用 `sendKey` 加密
- `src/shared/sync/syncSession.ts:509` `handleEncryptedFrame` 用 `receiveKey` 解密

**偏差理由**

单向密钥隔离可防止同一会话内的反射攻击（把 initiator 发出的密文原样回放给 initiator 触发其解密路径）；同时收发密钥独立轮换、独立泄露面。info 串中嵌入 `role->peerRole` 方向标记，保证两个方向的派生输入不同，无额外握手开销。

### 偏差 3：HKDF salt 构造方式

**设计文档原始描述**

第 5.2 节"传输加密"写出 HKDF 派生公式但未指定 salt 取值：

> 使用 `sharedSecret` 派生会话密钥：`HKDF-SHA256(sharedSecret, salt, 'taskflow-sync-v1')`。

**实现的实际做法**

salt 由双方 deviceId 与握手 nonce 排序后拼接再 sha256 得出，保证双方独立计算出相同 salt，且不同会话间 salt 不同：

- `src/shared/sync/syncSession.ts:491-499` `computeSessionKeys` 内构造 salt：
  ```
  sortedDeviceIds = [self.deviceId, peer.deviceId].sort()
  sortedNonces    = [self.nonce, peer.nonce].sort()
  saltInput = concat(sortedDeviceIds[0], sortedDeviceIds[1],
                     sortedNonces[0], sortedNonces[1])
  salt = sha256(saltInput)
  ```
- 排序保证双方视角下 salt 输入字节序一致；角色只决定 send/receive 方向，不影响 salt。
- `src/shared/sync/syncSession.ts:500` 把该 salt 传给 `deriveSessionKeys`。

**偏差理由**

ECDH 共享密钥本身已含熵，但 salt 引入握手 nonce 与双方身份，把密钥派生绑定到本次握手的两个具体身份与一次性 nonce，即便复用 ECDH 临时密钥（实际不会），不同 nonce 也会产出不同会话密钥；同时让密文与对端身份强绑定，缩小未知密钥共享（UKS）攻击面。设计文档预留了 salt 参数位但未指定取值，实现补全这一空缺。

### 偏差 5：移动端 ?token= 查询参数认证 + 活动检测

**设计文档原始描述**

第 7.2 节"接口（WebSocket）"列出：

```
POST /register-device
POST /claim-pairing-code
WS /sync?deviceId=...
```

WS 连接以 `deviceId` 作为查询参数，未提及 token 认证或连接活动检测。

**实现的实际做法**

移动端 RelayTransport 用 `?token=<bearer>` 替代 `?deviceId=` 在 WS URL 上做认证，并叠加 90s 活动超时 + 30s 检测周期：

- `src/shared/sync/relayTransport.ts:126-129` `buildAuthUrl` 把 token 拼到 WS URL：`${baseUrl}?token=${encodeURIComponent(token)}`
- `src/shared/sync/relayTransport.ts:41-43` 常量 `ACTIVITY_TIMEOUT_MS = 90_000`、`ACTIVITY_CHECK_INTERVAL_MS = 30_000`
- `src/shared/sync/relayTransport.ts:168-169` `handleMessage` 每收到一帧更新 `lastActivityAt`
- `src/shared/sync/relayTransport.ts:268-278` `startActivityCheck` 每 30s 检查一次，距上次活动超过 90s 则 `terminateWs` 触发重连

**偏差理由**

移动端 RN 内置 WebSocket 对自定义 header 的支持因平台而异且非标准，无法像桌面端 Node `ws` 那样走 `Authorization` header。改用 query param 在自托管 relay + TLS 场景下风险可控（token 24h TTL 且随 refresh 轮转），relay 服务端已扩展为 header / query 两种认证并存向后兼容。活动检测替代 ws ping/pong：RN WebSocket 不暴露 ping/pong 事件，relay 服务端每 30s 发 TCP ping（RN 自动回 pong），transport 监听任意 message 更新最后活动时间，超过 3 倍 ping 间隔无活动判定为半开连接并重连，覆盖 TCP keepalive 无法检测的半开场景。

### 偏差 7：sync_records.id 格式 + 版本向量

**设计文档原始描述**

第 6.3 节"冲突解决（MVP）"描述：

> 采用 **last-write-wins**：比较 `updated_at`，保留时间戳更大的版本。
> 版本字段 `version` 用于检测并发写入；如双方版本同时增加，后续可升级为 CRDT 或手动合并。

第 4.1 节 `sync_records` 表结构中 `id` 格式注释为 `table_name:record_id:v:version`，记录字段不含版本向量。

**实现的实际做法**

实现保留 updatedAt 的 LWW 作为主裁决，新增可选 `deviceVersion`（版本向量，`Record<deviceId, number>`）字段，仅当冲突双方都携带该字段时用它做因果偏序判定，把 LWW 无法区分的"同毫秒并发写入"细化为偏序结果：

- `src/shared/sync/syncMessages.ts:62` `WireSyncRecord` 增加可选字段 `deviceVersion?: Record<string, number>`
- `src/shared/sync/syncMessages.ts:174-180` `isVersionVector` 校验值必须为有限数，拒绝 NaN / Infinity 破坏偏序比较
- `src/shared/sync/syncMessages.ts:198-201` `isWireSyncRecord` 校验 `deviceVersion` 字段
- `src/shared/store/slices/syncSlice.ts:200-244` `resolveTaskConflict`：先比 updatedAt，仅当时间戳相等且双方均有 `deviceVersion` 时委托 `conflictResolver.resolveConflict` 做因果判定；返回 `concurrent` 时按用户 `conflictStrategy` 映射
- `src/shared/store/slices/syncSlice.ts:213-236` 版本向量分支；任一侧缺失 `deviceVersion` 时退化为纯 updatedAt LWW，保证 HTTP REST 模式与旧数据行为不变

**偏差理由**

纯 LWW 依赖时钟精度，移动设备时钟漂移或同毫秒并发写入会丢失有效更新。版本向量以设备为单位记录因果计数，在不依赖可信时钟的前提下判定两个版本是否存在因果关系（一方 happened-before 另一方）或真并发。仅在双方都携带向量时启用，向后兼容无向量的 HTTP REST 数据；`concurrent` 时不擅自合并，按用户策略映射，把语义上无法自动裁决的情况交还用户。这是向 CRDT 演进的中间步，未引入完整 CRDT 的复杂度。
